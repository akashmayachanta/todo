After: callers say what happened

Problem. Ticking a repeating task is written three times (TypeScript, reminders.rs, android.rs); the subtask duration roll-up and default reminder exist only in TypeScript, so a tick from a notification or the Android widget skips them. CLAUDE.md says rules belong in core/.

Solution. Core owns completing and reopening a task; every caller sends the intent, not a computed patch.

  • Locality: one place for recurrence
  • Leverage: four callers, one interface
  • Tests cross one seam (core/tests/ops.rs)
  • Delete two copies of DST shift
  • Widget and notification ticks roll up

Unconfirmed lead from the walk: TypeScript's recurrence rule appears to accept "every 0 days" where Rust rejects it, which would loop on an overdue task. Not run.

2. One module for what a view contains

Strong in-process

app/src/routes/tasks/+page.svelte (172–272, 343–468, 703–714, 912–919) · app/src/lib/components/tasks/pins.ts (pinView) · app/src/lib/components/tasks/taskFilters.ts · app/src-tauri/src/home_widget.rs (list, by_due)

↓

The Android home widget stays in Rust; it is the one copy that can't share TypeScript.

Problem. "Which tasks are in Today / Upcoming / a project / a section / a filter, in what order" is rebuilt in the page for the list, the board, the calendar, the modal's prev/next, and the counts, then again in pins.ts and in Rust; the copies already disagree (the widget's Today is flat, the pin's Today has no overdue split).

Solution. A pure TypeScript module answers it once for a view; the page's layouts and the pins render what it returns.

  • Locality: one definition of Today
  • Testable with no DOM
  • Page loses roughly 300 lines
  • Add-defaults live beside the group
  • New views cost one function

3. Pull the tasks store out of the page

Worth exploring local-substitutable

app/src/routes/tasks/+page.svelte (902–1055, 1228–1607) · app/src/routes/widget/pin/+page.svelte · app/src/routes/widget/quick/+page.svelte · app/src/lib/components/tasks/QuickAddDialog.svelte

Before: interface as wide as the implementation

interface
5 copies of task state · 35 async functions · 30 identical catch lines · callers re-send unchanged fields
implementation: one api call each

Create-a-task is written 5 times across the page, the quick add dialog and both widget windows.

After: small interface, behaviour behind it

interface
tasks · projects · sections + a few verbs
tasks store
show at once · save · put back on failure · keep every copy in step · tell the user

Two adapters behind it make the client seam real: Tauri in the app, in-memory in tests.

Problem. The page holds the tasks, every mutation, and the bookkeeping to keep five copies of task state in step; about 27 functions repeat try / save / replace-by-id / toast, and none can run without the page.

Solution. One store module owns the state and the mutations; the page, the pins and quick add call verbs on it.

  • Locality: rollback written once
  • Leverage: three windows, one store
  • First JS tests become possible
  • Page shrinks toward markup

Biggest change of the five, and the app has no JS test runner today, so it needs one added first.

5. Collapse the pass-throughs behind the data client

Speculative ports & adapters

app/src/lib/api.ts · app/src/lib/tasks/client.ts · app/src/app/tauriClient.ts · app/src-tauri/src/commands.rs · app/src-tauri/src/lib.rs · server/src/routes.rs

Before: one operation, seven files

After: one table of operations

page and widgets
↓
tasks client
operations, declared once
app commands and server routes both generated from it
core ops

Problem. The client interface has one adapter, so the seam is hypothetical, and four of the seven hops for a new operation are one-line forwarding; commands.rs claims to match the server routes one for one but has four operations the server lacks (section reorder, delete completed, profile get and update).

Solution. Declare each operation once and derive the forwarding from it, or drop the interface until a second adapter exists.

  • New operation touches two files
  • App and server can't drift
  • Partial updates stop re-sending fields

Speculative because the friction is tedium, not bugs, and candidate 3 would give this seam its second adapter anyway.

Top recommendation

1. Move the completion rules into core

It is the only candidate where users can already see wrong behaviour (a tick from a notification or the Android widget skips the duration roll-up), core already has tests to extend, and it removes rule code from the page before candidates 2 and 3 reshape it.

Cheapest warm-up if you want one first: candidate 4.
